## 1. Project context

Screen Time is a self-hosted parental screen-time limiter for one family. Kid devices (Android phone/tablet, Windows 11 PCs) enforce daily time limits locally; a TypeScript server on Docker holds the shared record; parents use a web app and an Android parent app. The whole system lives in one monorepo. The full specification is `docs/SPEC.md`; the order of work is `docs/BUILD-PLAN.md`. Repository rules for coding agents are in `AGENTS.md` at the repo root: read it first.

The server (`server/`, package `@screentime/server`) is a Hono app. It uses **Drizzle ORM** with the `pg` driver against **PostgreSQL 18**. Today the database has one table, `families`, created by the migration `server/drizzle/0000_init.sql`. The server applies every migration in `server/drizzle/` each time it starts (`server/src/db/migrate.ts`). Migrations are generated by `drizzle-kit` from `server/src/db/schema.ts`.

The system is multi-tenant: one server holds several families, and a family must never see another family's data. PostgreSQL **row-level security** (RLS) enforces that inside the database, so a bug in one API handler cannot leak data.

This card:

1. Adds **every table** from SPEC §6.1 to `server/src/db/schema.ts` and generates the migration `0001_tables`.
2. Adds a **hand-written** migration `0002_rls` that creates the database role `screentime_app` and a row-level security policy on every family-owned table.
3. Adds `withFamily(db, familyId, fn)`, the helper every later API handler uses to run its queries inside one family.
4. Adds database tests that prove the isolation, and a script that fills a development database with one family.

How the isolation works, so you understand what you are building:

- The server connects to PostgreSQL as the user that **owns** the tables (`screentime` in Docker Compose). The owner bypasses row-level security. Only sign-in and the super admin use this directly (later cards).
- For a family request, `withFamily` opens a transaction and runs `SET LOCAL ROLE screentime_app` and `SELECT set_config('app.family_id', '<family uuid>', true)`. From then on, every query in that transaction runs as `screentime_app`, which is **not** the owner, so the policies apply: it sees and writes only rows whose `family_id` equals `app.family_id`.
- `SET LOCAL` and `set_config(..., true)` both end with the transaction. The next request on the same pooled connection starts clean.
- When `app.family_id` is not set, `current_setting('app.family_id', true)` returns `''` or null. The policy turns `''` into null with `NULLIF`, and `family_id = null` is never true, so the role sees **nothing**. That is the safe default.

### 5.1 `server/src/db/schema.ts`

Replace the whole file. The `families` table is unchanged; every other table is new. Notes on the design, so you do not "fix" it:

- Ids that the server creates default to `uuidv7()`. Ids that devices or apps create offline (`time_requests`, `grants`, `usage_segments`, `kid_messages`, `sos_incidents`) have **no default**: the client always sends them, so re-sending is idempotent.
- Pools, forms and statuses are `text` with a `CHECK` constraint, not PostgreSQL enums, so new values can be added later by migration.
- Every table except `otp_codes` has `family_id`, even where it could be found through another table (`notification_prefs`, `sos_locations`, `sos_acks`). The policy needs the column on the row itself.
- Foreign keys use Drizzle's default `ON DELETE no action`. Nothing is deleted in v1 (rows are archived, disabled or revoked instead).

Why it looks like this:

- The `--> statement-breakpoint` lines are how the Drizzle migrator splits a file into statements. Keep every one, each on its own line.
- `CREATE ROLE` is inside a `DO` block with `IF NOT EXISTS` because roles belong to the whole PostgreSQL server, not one database: the role may already exist (for example from the test database). Running it twice must not fail.
- `ALTER DEFAULT PRIVILEGES` makes tables that later migrations create readable by `screentime_app` too. They still need their own policy (see 5.7).
- `otp_codes` holds sign-in codes for any email, not family data, so `screentime_app` gets no access at all.

After this, `server/drizzle/meta/_journal.json` has three entries with tags `0000_init`, `0001_tables` and `0002_rls`. Its `when` numbers are times and will differ from anyone else's; that is fine.

### 5.4 `server/src/db/family.ts`

```ts
import { sql } from 'drizzle-orm';
import type { Db } from './client.js';

/** The transaction handle that `withFamily` passes to its callback. */
export type FamilyTx = Parameters<Parameters<Db['transaction']>[0]>[0];

/**
 * Runs `fn` in a transaction that can only see and write rows of one family (row-level security,
 * drizzle/0002_rls.sql). Every family-scoped request handler uses this. Both settings end with the
 * transaction, so a pooled connection never leaks one family's scope into the next request.
 */
export async function withFamily<T>(db: Db, familyId: string, fn: (tx: FamilyTx) => Promise<T>): Promise<T> {
  return db.transaction(async (tx) => {
    await tx.execute(sql`SET LOCAL ROLE screentime_app`);
    await tx.execute(sql`SELECT set_config('app.family_id', ${familyId}, true)`);
    return fn(tx);
  });
}
```

### 5.6 `server/scripts/seed-dev.ts`

A development helper, not part of the server build (the server's `tsconfig.json` only includes `src/`). It applies migrations, then creates one family in a single transaction. It connects as the owner, so row-level security does not apply to it.

```ts
// Fills an empty development database with one family, so later cards have data to work with.
// Usage (from the repo root, with DATABASE_URL set): pnpm --filter @screentime/server exec tsx scripts/seed-dev.ts you@example.com
// Never run this against the production database.
import { randomBytes } from 'node:crypto';
import { eq } from 'drizzle-orm';
import { createDb } from '../src/db/client.js';
import { runMigrations } from '../src/db/migrate.js';
import { families, kids, messagePresets, parents, scheduleVersions } from '../src/db/schema.js';

const BASE32 = 'ABCDEFGHIJKLMNOPQRSTUVWXYZ234567';

/** RFC 4648 base32 without padding, as authenticator apps expect. */
function base32(bytes: Uint8Array): string {
  let bits = 0;
  let value = 0;
  let out = '';
  for (const byte of bytes) {
    value = (value << 8) | byte;
    bits += 8;
    while (bits >= 5) {
      out += BASE32[(value >>> (bits - 5)) & 31];
      bits -= 5;
    }
  }
  if (bits > 0) out += BASE32[(value << (5 - bits)) & 31];
  return out;
}

/** ISO weekday 1 = Monday ... 7 = Sunday (docs/SPEC.md §6.1 schedule_versions). */
function week() {
  return [1, 2, 3, 4, 5, 6, 7].map((weekday) =>
    weekday <= 5
      ? { weekday, screensMin: 120, phoneMin: 90, wake: '07:00', bedtime: '20:30' }
      : { weekday, screensMin: 180, phoneMin: 120, wake: '08:00', bedtime: '21:00' },
  );
}

const PRESETS = [
  'Can I have more time?',
  "I'm done, you can lock it",
  'Can you call me?',
  "I'm on my way home",
  'I need help with homework',
];

const databaseUrl = process.env.DATABASE_URL;
const email = process.argv[2]?.trim().toLowerCase();
if (!databaseUrl || !email) {
  console.error('Usage: DATABASE_URL=postgres://... tsx scripts/seed-dev.ts <parent-email>');
  process.exit(1);
}

const { db, pool } = createDb(databaseUrl);
try {
  await runMigrations(db);
  const existing = await db.select().from(parents).where(eq(parents.email, email));
  if (existing.length > 0) {
    console.error(`A parent with email ${email} already exists. Nothing changed.`);
    process.exitCode = 1;
  } else {
    await db.transaction(async (tx) => {
      const [family] = await tx
        .insert(families)
        .values({ name: 'Dev family', timezone: 'Australia/Sydney', parentCodeSecret: base32(randomBytes(20)) })
        .returning();
      if (!family) throw new Error('family insert returned nothing');
      const [parent] = await tx
        .insert(parents)
        .values({ familyId: family.id, email, displayName: 'Dad' })
        .returning();
      if (!parent) throw new Error('parent insert returned nothing');
      const kidRows = await tx
        .insert(kids)
        .values([
          { familyId: family.id, name: 'Alex', avatarColor: '#0F766E' },
          { familyId: family.id, name: 'Sam', avatarColor: '#7C3AED' },
        ])
        .returning();
      await tx.insert(scheduleVersions).values(
        kidRows.map((kid) => ({ familyId: family.id, kidId: kid.id, version: 1, days: week(), createdBy: parent.id })),
      );
      await tx
        .insert(messagePresets)
        .values(PRESETS.map((text, sort) => ({ familyId: family.id, text, sort })));
      console.log(`Seeded family ${family.id} with parent ${email} and kids Alex and Sam.`);
    });
  }
} finally {
  await pool.end();
}
```

### 6.2 Row-level security

- Role `screentime_app`: `NOLOGIN`. Privileges: `USAGE` on schema `public`; `SELECT, INSERT, UPDATE, DELETE` on every table except `otp_codes`.
- Every family-scoped table: `ENABLE ROW LEVEL SECURITY` and one policy named `family_isolation` for all commands, with the same expression in `USING` (which rows can be seen, updated, deleted) and `WITH CHECK` (which rows can be inserted, or what an update may change a row into):
  `family_id = NULLIF(current_setting('app.family_id', true), '')::uuid` (for `families`: `id = ...`).
- A violation raises PostgreSQL error code `42501` (`new row violates row-level security policy` or `permission denied`). Reads and updates of other families' rows do not raise: they just see zero rows.

### 6.3 `withFamily(db, familyId, fn)`

- Opens a Drizzle transaction, runs `SET LOCAL ROLE screentime_app`, then `SELECT set_config('app.family_id', <familyId>, true)` with the id as a bound parameter (never string-concatenated), then `return fn(tx)`.
- If `fn` throws, the transaction rolls back and the error propagates.
- Returns whatever `fn` returns.

### 6.4 Seed script

- Arguments: one parent email (lower-cased and trimmed). Needs `DATABASE_URL`. Missing either: prints the usage line to stderr and exits with code 1.
- Applies migrations first.
- If a parent with that email exists: prints `A parent with email <email> already exists. Nothing changed.` and exits with code 1.
- Otherwise, in one transaction: family `Dev family`, time zone `Australia/Sydney`, a random 20-byte parent-code secret in base32 (32 characters); parent `Dad` with that email; kids `Alex` (`#0F766E`) and `Sam` (`#7C3AED`); for each kid schedule version 1 (Monday to Friday 120 min Screens, 90 min Phone, wake 07:00, bedtime 20:30; Saturday and Sunday 180, 120, 08:00, 21:00); the five SPEC message presets in order. Prints `Seeded family <uuid> with parent <email> and kids Alex and Sam.`
